Why the count looks low

Only 2 of 29 checks are fully done because A-01 was built and debugged for exactly one job: strip client identity, exhaustively, across text/images/metadata/hyperlinks/comments — and it does that job well (five independent verification channels, 19 real bugs found and fixed against a real 57-image deck). The checklist asks for a broader guarantee — commercial terms, competitive intel, sensitive outcomes, legal sign-off — that the agent was never scoped to cover. The gap is scope, not reliability.

03

Gap catalogue — the seven things to design

The 24 partial/gap items above collapse into seven design problems (the People and Technical/Screenshots partial items close alongside their category's gap fix). Each states what's missing, why the current architecture doesn't catch it, and the technical closure design.

P1

A · Commercial & Financial Terms (3.1—3.3)

Root cause: the taxonomy has an explicit row keeping deal dollar amounts by default — correct for an internal record, wrong for something meant to leave the building.
Design
  • New entity type COMMERCIAL_TERM — regex pre-pass for currency/percentage/payment-term patterns (free) feeding the Detector for contextual classification (a $ figure near "trial balance" isn't a commercial-term hit; one near "contract value" is).
  • Default action is flag, not mask — a case study often needs a figure to stay credible ("saved $2M annually"). Reviewer chooses keep / generalize ("$2M" — "multi-million dollar") / remove.
P2

B · Infrastructure, Security & Credentials (4.1—4.3)

Root cause: the pre-pass pattern library only knows identity shapes (emails, org/person names) — nothing about hostnames, IP ranges, or secret formats.
Design
  • Fully deterministic, no LLM needed — cheapest gap on this list. IPv4/IPv6 ranges, internal-hostname patterns, and credential shapes (AWS-style keys, bearer tokens, connection strings) are all reliably regex-matched.
  • New entity types INFRA_IDENTIFIER (mask) and CREDENTIAL (mandatory redaction — reuses the exact server-side-enforced override already built for confirmed own-firm logo matches, since a live credential should never be reviewer-overridable).
  • Extends the vision-scan prompt (already firing on every image) to also flag visible credentials/hostnames in a screenshot — shared work with Gap D below, not a separate feature.
P1

C · Data Samples in Screenshots, Datasets & Reports (5.1—5.3)

Root cause: the vision call asks exactly one question — does this image reveal client identity (logo/wordmark). It's never asked whether the image's content is real, unmasked client data.
Design
  • Add a second structured field, contains_real_data_sample, to the existing per-image vision call — same call already firing for logo detection, no added vision cost.
  • New candidate type DATA_SAMPLE_IMAGE, reviewer chooses redact / replace-with-placeholder / approve.
  • Sample-dataset provenance (5.2) is a narrower, code-only check: flag any dataset file whose path/filename matches a client account already linked in the source registry — reuses the existing protected lookup, no new detection.
P2

D · Technical Diagrams & Screenshot Visible Text (4.4, 10.1)

Root cause: images are only interpreted for branding, never for the text rendered inside them — an architecture diagram's system-name labels and a UI screenshot's visible email/dollar-figure/URL text are equally invisible to the current pipeline.
Design
  • Extend the same vision call again with visible_sensitive_text — OCR/vision reads text baked into the image and classifies it against the same entity taxonomy already used for document prose (client names, system names, commercial terms, infra identifiers all apply here too).
  • One shared extension serves diagrams (4.4), screenshots (10.1), and feeds Gap B's credential/hostname check in images — three checklist items closed by one prompt change.
P2

E · Competitive & Strategic Information (6.1—6.3)

Root cause: this is contextual, judgment-heavy prose ("the client is evaluating a divestiture of...") — structurally not name-shaped or number-shaped, so no regex pre-pass can catch it and the current Detector skill is scoped to identity, not strategy.
Design
  • New skill competitive-strategic-detection, loaded by the Detector alongside sanitization-detection, flags competitor references and forward-looking strategic language.
  • Flag-for-review, never auto-mask — this content is often the most narratively important part of the case study. Confirmed competitor names resolve through the existing dictionary/alias mechanism once approved.
P2

F · Sensitive Outcomes (7.1—7.3)

Root cause: this is the clearest case where "detect and mask" is the wrong shape — a root-cause narrative or a negative metric is often exactly what makes a case study credible, and whether it's safe to publish is a client-relationship judgment call, not a text pattern.
Design
  • Extend the Summarizer's existing metadata draft with a boolean discusses_negative_outcome plus the specific sentence(s), surfaced as a distinct, non-dismissible reviewer callout — same surfacing pattern as a low-confidence entity today, not a confirmed mask.
  • Reviewer decision (approve-as-is / requires client sign-off / remove) is recorded in the run's audit trail — this is where the checklist's own client-approval step plugs directly into the review UI.
P2

G · Own IP, Methodology & Cost Structure (2.2, 2.3, 8.1, 8.2)

Root cause: the three-layer own-firm exclusion exists to keep NaviKenz's own identity visible (correct for branding) — it has no opposite-direction check for internal cost/staffing detail or org-chart-shaped content, client-side or own-side.
Design
  • New entity type OWN_COST_DETAIL (staffing ratios, day-rate/FTE figures, exact accelerator configs) — same regex+contextual-classification pattern as COMMERCIAL_TERM, scoped to sentences where the subject is the delivery firm.
  • New entity type ORG_CHART_STRUCTURE — detects reporting-line diagrams and structured name/title pairs (client or internal), flagged for genericization.
  • New per-person consent_status on internal team members in the masking dictionary — internal names default to "keep" only once explicit consent is on record; absent consent, they route to the same flag-for-review queue as everything else in this group.

Mask vs. Flag is the load-bearing distinction, not the entity list itself

Every existing identity entity is a hard mask — there's no legitimate reason a client's real name should survive into a distributed case study. Nearly everything added here defaults to flag, because a case study's whole purpose is to convey real outcomes, numbers, and methodology — the checklist itself says "approved for sharing," not "always remove." Auto-masking these would silently gut the document's credibility; a reviewer decision is the correct default, same discipline as A-03's Tier-1/Tier-2 split for destructive actions.

08

Process & governance — the distribution-tier gate

The checklist already has a natural gate built in — "Approved for Distribution To: Internal only / Sales-Marketing / Public-External." Not every category needs to be clean for an internal share; all of them do before something goes external. This reuses the tiered-strictness philosophy already proven in the SharePoint Cleanup Agent's Tier-1/Tier-2 model (sharepoint_cleaning_agent_master_design.html Sec. 07): what requires review is decided by the destination, not by model confidence.

Internal only

  • Client identity masked (1—2)
  • Credentials never allowed through, any tier
  • No commercial/strategic/outcome gate required

Sales / Marketing

  • Everything in Internal, plus:
  • Commercial-term flags resolved (3)
  • Competitive/strategic flags resolved (6)
  • Data-sample image flags resolved (5)

Public / External

  • Everything in Sales/Marketing, plus:
  • Sensitive-outcome client sign-off recorded (7)
  • Legal attestation complete (9)
  • Own-IP/cost detail flags resolved (8)

Legal & Contractual Constraints — the one gate that isn't agent detection

MSA/NDA confidentiality clauses, case-study pre-approval status, and data-residency/compliance obligations cannot be answered by reading the document — they live in a contract NaviKenz holds, not in the file's text. legal_attestation.record is a governance-only write: three booleans plus a note, set by km_governance, the same role that already owns mask approval and client-account linkage.

distribution_gate.evaluate blocks the "mark ready for public distribution" action in the review UI until the attestation record exists and every flag in the run is resolved — exactly the way A-03 blocks Tier-2 actions on a missing eligibility rule.

draft— flags open— tier requested— gate blockedor gate cleared — ready to distribute
09

Build plan & phasing

Ordered by a mix of checklist risk (what's most likely to actually leak in a real case study) and build cost (deterministic extensions ship fastest).

P1

Commercial terms + Data-sample images

Highest exposure

Most likely to appear in every real case study (dollar figures and screenshots are ubiquitous), and furthest from the checklist's intent today.

  • Add COMMERCIAL_TERM regex pattern set + wire commercial-term-detection skill into the Detector.
  • Add contains_real_data_sample field to the existing vision call; one-line prompt change, no new model calls.
  • Build flags.py (flag_for_judgment.create/resolve) and the flagged_items table — shared infrastructure the rest of the plan reuses.
P2

Infra/credentials + Diagram/screenshot text + Competitive/strategic + Sensitive outcomes + Own-IP/cost + Org chart + Consent

Structural additions

Infra/credentials is pure deterministic regex — cheapest of the group, can run alongside P1 if capacity allows. The rest share the flagged_items mechanism built in P1, so each is a skill + a small prompt/field addition, not new infrastructure.

  • infra_credential.py + CREDENTIAL mandatory-redaction wiring.
  • Vision-scan visible_sensitive_text field (closes 4.4 + 10.1 together).
  • competitive-strategic-detection, sensitive-outcome-flagging, own-side-cost-detection, org-chart-detection skills.
  • consent_status column + reviewer UI toggle for internal-team entities.
P3

Distribution-tier gate + Legal attestation + EXIF strip

Governance layer

Sequenced last deliberately — the gate consumes the flags produced by P1/P2, so it can't meaningfully ship before there's a sensitive-outcome flag or commercial-term flag to gate on. EXIF stripping is independent and can move earlier if a quick win is wanted.

  • legal_attestation table + governance-only CRUD.
  • distribution_gate.evaluate + DistributionGatePanel.jsx.
  • exif_strip.py + sixth verification channel (verified_image_metadata).
P4

Advanced Policy-Based Sanitization

Policy layer

Sequenced after P1-P3 for the same reason the governance gate was: a configurable rule engine and a 4-level policy hierarchy have nothing to enforce until flagged_items, the entity taxonomy (Sec. 04), and the 3-tier distribution gate (Sec. 08) already exist. P4 doesn't rebuild that infrastructure — it generalizes it into an organization-configurable policy layer. Full design in Sec. 12.

  • Rule engine (regex/dictionary/keyword/metadata/file-type/org-custom) running ahead of the LLM Detector — formalizes the free pre-pass pattern already used since P1/P2.
  • Four default policy profiles (Internal / Cross-Practice / External Partner / Public) superseding the 3-tier distribution_tier enum with a finer policy_level, migration-mapped so no P3 run breaks.
  • Reviewer override path + audit trail, reusing the existing audit_log.write call from Gap F (Sec. 11).

Same cost lever as the original regex/NER pre-pass, generalized and made org-configurable.
4 levels, not 3The Sec. 08 distribution gate's Internal/Sales-Marketing/Public-External split is kept, not replaced — Phase 4's hierarchy (Sec. 12.2) refines it by splitting "Internal" into Internal Team and Internal Cross-Practice, and adding a new External Partner level between Sales-Marketing and Public for NDA'd third parties the original 3-tier model had no slot for.
Policy is data, not codeSanitization profiles are YAML/JSON, loaded per run by a new Profile Loader (Sec. 12.6/12.7) — an organization tunes its own thresholds, custom rules, and level definitions without a code deploy, the same "config over code" preference already used for the masking-style skill's token format.
Overrides are logged, mandatory items aren't overridableAny policy decision below Priority 0 can be reviewer-overridden with a reason code, written to a new audit table (Sec. 12.5) — but CREDENTIAL and other mandatory-redaction entities stay non-overridable at every level, unchanged from the rule already built in Gap B (Sec. 11).
One arbitration authority, not two"Policy Resolution Engine" (Sec. 12.7) is a named responsibility of the Policy Evaluator, not a second component built alongside it — conflicts between the rule engine, the LLM Detector, org overlays, and consent records are arbitrated in exactly one place, by one published precedence order, so there's never a question of which of two arbiters ran last.
Audit entries are append-only and policy-version-stampedEvery decision writes a hash-chained, immutable entry naming the exact policy_version that produced it (Sec. 12.5/12.7) — a profile can be revised (a new published version) without invalidating what an already-completed run's audit trail says happened, which is what an auditor re-checking a run six months later actually needs.

12

Phase 4 — Advanced Policy-Based Sanitization

Everything in Sec. 01-11 closes specific checklist gaps with specific entity types, skills, and a 3-tier distribution gate. Phase 4 sits one layer above that: it generalizes the mask/flag decision itself into a configurable, audience-aware policy, so that which action applies to which entity is driven by data an organization can edit — not by logic hardcoded into the Detector. Nothing here replaces the taxonomy (Sec. 04), skills (Sec. 05), protected calls (Sec. 06), or the flagged_items/audit infrastructure built in Sec. 08 and Sec. 11 — Phase 4 plugs into all four.

What changes vs. Sec. 01-11

Before Phase 4: an entity's default action (mask/flag/keep) is fixed per entity type, and "how strict" is a single 3-way distribution-tier gate checked once at the end.

After Phase 4: an entity's action is resolved per policy level from a profile the organization owns, deterministic rules run before any LLM call to cut cost, and reviewers can override any non-mandatory decision with a logged reason — same entities, same skills, more configurable strictness.

12.1 Policy-driven rule engine

A configurable, deterministic engine that runs before the LLM Detector ever sees a chunk — it formalizes the free regex/NER pre-pass pattern already used since Gap A/B (Sec. 11) into six rule types an organization can extend without touching agent code. It is "policy-driven" rather than a bare pattern matcher: a rule's match doesn't apply an action by itself, it produces a candidate that the Policy Resolution Engine (Sec. 12.7) merges against the requested hierarchical level and any LLM Detector finding before one final action is written.

Rule priority & conflict resolution

PriorityRule sourceReviewer-overridable?
0 — MandatorySystem-level rules for credentials and legal holdsNever
1 — Org-customOrganization's own compliance-team additions, ranked above the generic libraryYes
2 — Built-in deterministicThe platform's own regex/dictionary/keyword libraryYes
3 — Metadata rulesFile-level signals (classification tags, EXIF flags)Yes
4 — File-type defaultFallback baseline per file format when nothing more specific firesYes

Conflict resolution: most restrictive action wins

When two rules fire on the same span at different priority tiers, the engine does not simply take the higher-priority tier's answer — it applies whichever action is more restrictive on a fixed scale: Mandatory Redact > Remove > Generalize > Mask > Flag > Keep. A Priority-4 file-type default that says "remove" beats a Priority-2 library rule that only says "mask." Every rule that matched is still recorded against the span for the reviewer, even the ones that lost the tie — nothing is silently dropped from the audit trail.

Cost effect: every span this engine resolves with certainty is one the LLM Detector never has to reason about. As an organization adds its own custom rules (Priority 1), the deterministic share of each document grows and per-document LLM spend shrinks accordingly — the same lever already proven in Sec. 10's "deterministic-first" decision, now extended to all six rule types instead of just the original three regex pattern files.

This tie-break is the rule engine's own internal arbitration — resolving which rule wins when several rules fire. It is one input to the broader Policy Resolution Engine (Sec. 12.7), which additionally arbitrates between this engine's output, the LLM Detector's contextual finding, and the requested hierarchical level, since those three can each suggest a different action for the same entity.

12.2 Hierarchical sanitization

Four sanitization levels, escalating by intended recipient. Each level inherits everything the level below it requires, then adds more.

L1 · Internal Team

  • Minimal masking — only CREDENTIAL is mandatory-redacted
  • Client identity, infra identifiers, commercial terms, and strategy all kept
  • Preserves full business context for the delivery team itself

L2 · Internal Cross-Practice

  • Everything in L1, plus:
  • Client identity masked (name, brand, location, person)
  • Infrastructure identifiers masked
  • Commercial terms, strategy, and own-cost detail still kept — audience is trusted staff outside the account team

L3 · External Partner

  • Everything in L2, plus:
  • Commercial terms removed or generalized
  • Architecture/diagram details removed
  • Internal methodology and own-cost detail generalized
  • Competitor and strategy mentions flagged for review

L4 · Public Case Study

  • Everything in L3, plus:
  • Maximum sanitization, generic company naming
  • Real-data screenshots replaced with synthetic equivalents
  • Strategy, financial specifics, credentials, and competitor names all removed
  • Sensitive-outcome client sign-off mandatory before publish

The full per-entity breakdown of what's masked, flagged, generalized, or removed at each level is the Policy Matrix below — the level cards above are the summary, the matrix is the source of truth.

12.5 Reviewer overrides

A reviewer can override any policy-matrix or rule-engine decision that isn't Priority 0 — for example, keeping a COMMERCIAL_TERM the L3 profile would otherwise generalize, because the reviewer judges this particular figure safe. Every override requires a reason code and is written to a new audit table before it takes effect; the entity's original (policy-computed) action is preserved alongside the override so the two are never conflated in the audit trail.

CallTypeRoleStatus
policy_override.recordProtectedWrites a reviewer override (entity/span, original action, override action, reason code, reviewer_id) to policy_overrides. Rejected outright for any Priority-0 entity — same non-overridable enforcement already built for CREDENTIAL in Gap B (Sec. 11).New

Mandatory items stay mandatory

Overrides exist so a case study doesn't lose its narrative value to an overly blunt policy default — they do not exist to let a reviewer republish a credential or bypass a client sign-off requirement. policy_override.record checks the entity's priority tier before writing anything; a Priority-0 attempt is rejected at the call itself, not merely discouraged in the UI.

Immutable audit logging & policy versioning

Every decision this pipeline makes — a rule-engine match, an LLM Detector finding, the Hierarchical Policy Resolution Engine's merged action, or a reviewer override — writes one append-only entry to the run's audit log. Entries are never updated or deleted, only superseded by a new entry that points back at the one it revises, so the full decision history for a run is always reconstructable, not just its final state.

  • Tamper-evident, not just append-only. Each entry stores a hash of the previous entry in the same run alongside its own content hash, so any out-of-band edit to a stored entry breaks the chain and is detectable on the next audit read — the same tamper-evidence property Sec. 09's legal/contractual gate implicitly assumes when it treats an attestation record as trustworthy.
  • Every entry is policy-version-stamped. An entry doesn't just say "masked" — it records the exact policy_version of the profile that produced that action. If an organization later publishes a new version of its L3 profile, every prior run's audit trail still shows, correctly, which version governed it at the time.
  • Versioning is append-only too. A published policy version is immutable once live — changing a rule means publishing version n+1, never editing version n in place. This is what makes a run reproducible months later: re-running the same document against the policy_version pinned in its audit trail must always yield the same decisions.

12.6 Configuration — policy as data

Each policy level is a YAML/JSON profile, not a code path. Profiles can extend a parent level and layer an organization's own custom rules on top, so a client-specific compliance requirement never means a code deploy. Illustrative shape (not literal implementation):

profile: level_3_external_partner
extends: level_2_cross_practice
# rule engine additions layered on top of the built-in library
rules:
  - type: regex
    pattern: commercial_term_currency
    action: generalize
    priority: 2
  - type: org_custom
    org: acme-corp
    pattern: internal_project_codename
    action: remove
    priority: 1
# per-entity policy overrides for this level
entities:
  COMMERCIAL_TERM: { action: generalize, reviewer_required: true }
  INFRA_IDENTIFIER: { action: mask, reviewer_required: false }
  CREDENTIAL: { action: mandatory_redact, reviewer_required: false, overridable: false }

Four default profiles ship with the platform (L1-L4, Sec. 12.2). An organization's overlay is a separate file merged on top at load time by the Sanitization Profile Loader (Sec. 12.7) — the defaults stay intact for every other org. The Profile Loader never reads a profile off disk by mutable path — it fetches a specific, published version from the Policy Repository (Sec. 12.7), so a profile referenced by a run in progress can't change underneath it.
