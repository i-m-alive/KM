Case Study Sanitization Checklist — every item, what's done, what's not, and how we close the rest

A full item-by-item audit of the 29 checks in the Case Study Sanitization Checklist against the Sanitization Agent (A-01) as actually built and debugged — not the design intent, the validated behavior. Where the checklist isn't met, this document designs the technical closure: new entity types, new skills, new protected calls, the data model and file changes they need, and the review/governance process that ties it all to the checklist's own distribution-approval field.

Why the count looks low

Only 2 of 29 checks are fully done because A-01 was built and debugged for exactly one job: strip client identity, exhaustively, across text/images/metadata/hyperlinks/comments — and it does that job well (five independent verification channels, 19 real bugs found and fixed against a real 57-image deck). The checklist asks for a broader guarantee — commercial terms, competitive intel, sensitive outcomes, legal sign-off — that the agent was never scoped to cover. The gap is scope, not reliability.

03

Gap catalogue — the seven things to design

The 24 partial/gap items above collapse into seven design problems (the People and Technical/Screenshots partial items close alongside their category's gap fix). Each states what's missing, why the current architecture doesn't catch it, and the technical closure design.

P1

A · Commercial & Financial Terms (3.1–3.3)

Root cause: the taxonomy has an explicit row keeping deal dollar amounts by default — correct for an internal record, wrong for something meant to leave the building.
Design
  • New entity type COMMERCIAL_TERM — regex pre-pass for currency/percentage/payment-term patterns (free) feeding the Detector for contextual classification (a $ figure near "trial balance" isn't a commercial-term hit; one near "contract value" is).
  • Default action is flag, not mask — a case study often needs a figure to stay credible ("saved $2M annually"). Reviewer chooses keep / generalize ("$2M" → "multi-million dollar") / remove.
P2

B · Infrastructure, Security & Credentials (4.1–4.3)

Root cause: the pre-pass pattern library only knows identity shapes (emails, org/person names) — nothing about hostnames, IP ranges, or secret formats.
Design
  • Fully deterministic, no LLM needed — cheapest gap on this list. IPv4/IPv6 ranges, internal-hostname patterns, and credential shapes (AWS-style keys, bearer tokens, connection strings) are all reliably regex-matched.
  • New entity types INFRA_IDENTIFIER (mask) and CREDENTIAL (mandatory redaction — reuses the exact server-side-enforced override already built for confirmed own-firm logo matches, since a live credential should never be reviewer-overridable).
  • Extends the vision-scan prompt (already firing on every image) to also flag visible credentials/hostnames in a screenshot — shared work with Gap D below, not a separate feature.
P1

C · Data Samples in Screenshots, Datasets & Reports (5.1–5.3)

Root cause: the vision call asks exactly one question — does this image reveal client identity (logo/wordmark). It's never asked whether the image's content is real, unmasked client data.
Design
  • Add a second structured field, contains_real_data_sample, to the existing per-image vision call — same call already firing for logo detection, no added vision cost.
  • New candidate type DATA_SAMPLE_IMAGE, reviewer chooses redact / replace-with-placeholder / approve.
  • Sample-dataset provenance (5.2) is a narrower, code-only check: flag any dataset file whose path/filename matches a client account already linked in the source registry — reuses the existing protected lookup, no new detection.
P2

D · Technical Diagrams & Screenshot Visible Text (4.4, 10.1)

Root cause: images are only interpreted for branding, never for the text rendered inside them — an architecture diagram's system-name labels and a UI screenshot's visible email/dollar-figure/URL text are equally invisible to the current pipeline.
Design
  • Extend the same vision call again with visible_sensitive_text — OCR/vision reads text baked into the image and classifies it against the same entity taxonomy already used for document prose (client names, system names, commercial terms, infra identifiers all apply here too).
  • One shared extension serves diagrams (4.4), screenshots (10.1), and feeds Gap B's credential/hostname check in images — three checklist items closed by one prompt change.
P2

E · Competitive & Strategic Information (6.1–6.3)

Root cause: this is contextual, judgment-heavy prose ("the client is evaluating a divestiture of...") — structurally not name-shaped or number-shaped, so no regex pre-pass can catch it and the current Detector skill is scoped to identity, not strategy.
Design
  • New skill competitive-strategic-detection, loaded by the Detector alongside sanitization-detection, flags competitor references and forward-looking strategic language.
  • Flag-for-review, never auto-mask — this content is often the most narratively important part of the case study. Confirmed competitor names resolve through the existing dictionary/alias mechanism once approved.
P2

F · Sensitive Outcomes (7.1–7.3)

Root cause: this is the clearest case where "detect and mask" is the wrong shape — a root-cause narrative or a negative metric is often exactly what makes a case study credible, and whether it's safe to publish is a client-relationship judgment call, not a text pattern.
Design
  • Extend the Summarizer's existing metadata draft with a boolean discusses_negative_outcome plus the specific sentence(s), surfaced as a distinct, non-dismissible reviewer callout — same surfacing pattern as a low-confidence entity today, not a confirmed mask.
  • Reviewer decision (approve-as-is / requires client sign-off / remove) is recorded in the run's audit trail — this is where the checklist's own client-approval step plugs directly into the review UI.
P2

G · Own IP, Methodology & Cost Structure (2.2, 2.3, 8.1, 8.2)

Root cause: the three-layer own-firm exclusion exists to keep NaviKenz's own identity visible (correct for branding) — it has no opposite-direction check for internal cost/staffing detail or org-chart-shaped content, client-side or own-side.
Design
  • New entity type OWN_COST_DETAIL (staffing ratios, day-rate/FTE figures, exact accelerator configs) — same regex+contextual-classification pattern as COMMERCIAL_TERM, scoped to sentences where the subject is the delivery firm.
  • New entity type ORG_CHART_STRUCTURE — detects reporting-line diagrams and structured name/title pairs (client or internal), flagged for genericization.
  • New per-person consent_status on internal team members in the masking dictionary — internal names default to "keep" only once explicit consent is on record; absent consent, they route to the same flag-for-review queue as everything else in this group.

Mask vs. Flag is the load-bearing distinction, not the entity list itself

Every existing identity entity is a hard mask — there's no legitimate reason a client's real name should survive into a distributed case study. Nearly everything added here defaults to flag, because a case study's whole purpose is to convey real outcomes, numbers, and methodology — the checklist itself says "approved for sharing," not "always remove." Auto-masking these would silently gut the document's credibility; a reviewer decision is the correct default, same discipline as A-03's Tier-1/Tier-2 split for destructive actions.

08

Process & governance — the distribution-tier gate

The checklist already has a natural gate built in — "Approved for Distribution To: Internal only / Sales-Marketing / Public-External." Not every category needs to be clean for an internal share; all of them do before something goes external. This reuses the tiered-strictness philosophy already proven in the SharePoint Cleanup Agent's Tier-1/Tier-2 model (sharepoint_cleaning_agent_master_design.html §07): what requires review is decided by the destination, not by model confidence.

Internal only

  • Client identity masked (1–2)
  • Credentials never allowed through, any tier
  • No commercial/strategic/outcome gate required

Sales / Marketing

  • Everything in Internal, plus:
  • Commercial-term flags resolved (3)
  • Competitive/strategic flags resolved (6)
  • Data-sample image flags resolved (5)

Public / External

  • Everything in Sales/Marketing, plus:
  • Sensitive-outcome client sign-off recorded (7)
  • Legal attestation complete (9)
  • Own-IP/cost detail flags resolved (8)

Legal & Contractual Constraints — the one gate that isn't agent detection

MSA/NDA confidentiality clauses, case-study pre-approval status, and data-residency/compliance obligations cannot be answered by reading the document — they live in a contract NaviKenz holds, not in the file's text. legal_attestation.record is a governance-only write: three booleans plus a note, set by km_governance, the same role that already owns mask approval and client-account linkage.

distribution_gate.evaluate blocks the "mark ready for public distribution" action in the review UI until the attestation record exists and every flag in the run is resolved — exactly the way A-03 blocks Tier-2 actions on a missing eligibility rule.

draft→ flags open→ tier requested→ gate blockedor gate cleared → ready to distribute
09

Build plan & phasing

Ordered by a mix of checklist risk (what's most likely to actually leak in a real case study) and build cost (deterministic extensions ship fastest).

P1

Commercial terms + Data-sample images

Highest exposure

Most likely to appear in every real case study (dollar figures and screenshots are ubiquitous), and furthest from the checklist's intent today.

  • Add COMMERCIAL_TERM regex pattern set + wire commercial-term-detection skill into the Detector.
  • Add contains_real_data_sample field to the existing vision call; one-line prompt change, no new model calls.
  • Build flags.py (flag_for_judgment.create/resolve) and the flagged_items table — shared infrastructure the rest of the plan reuses.
P2

Infra/credentials + Diagram/screenshot text + Competitive/strategic + Sensitive outcomes + Own-IP/cost + Org chart + Consent

Structural additions

Infra/credentials is pure deterministic regex — cheapest of the group, can run alongside P1 if capacity allows. The rest share the flagged_items mechanism built in P1, so each is a skill + a small prompt/field addition, not new infrastructure.

  • infra_credential.py + CREDENTIAL mandatory-redaction wiring.
  • Vision-scan visible_sensitive_text field (closes 4.4 + 10.1 together).
  • competitive-strategic-detection, sensitive-outcome-flagging, own-side-cost-detection, org-chart-detection skills.
  • consent_status column + reviewer UI toggle for internal-team entities.
P3

Distribution-tier gate + Legal attestation + EXIF strip

Governance layer

Sequenced last deliberately — the gate consumes the flags produced by P1/P2, so it can't meaningfully ship before there's a sensitive-outcome flag or commercial-term flag to gate on. EXIF stripping is independent and can move earlier if a quick win is wanted.

  • legal_attestation table + governance-only CRUD.
  • distribution_gate.evaluate + DistributionGatePanel.jsx.
  • exif_strip.py + sixth verification channel (verified_image_metadata).

Detailed implementation plan — resolving every gap against the current agent

This is the "how," underneath §03's "what" and §09's "when." Each gap below is broken into concrete implementation steps against the actual current codebase (file names as listed in the live debugging report's appendix), in build order, ending with the regression-suite coverage that proves it before it ever touches a real document — the same discipline that caught real bugs (issues 16 and 17 in the debugging report) before they reached production. P1/P2/P3 labels match §03/§09 — this section doesn't re-sequence anything, it just fills in the steps under each label.

A · Commercial & Financial Terms P1

1

Detection — new regex layer

New app/agents/sanitization/regex_patterns/commercial_terms.py: currency amounts, percentage figures, and payment-term keyword phrases ("net 30", "penalty clause", "SLA credit", "rate card"). Wired into ner_prepass.py's existing candidate-generation pass, free and on-CPU, same as today's regex/NER candidates.

2

Detector + skill

New skill commercial-term-detection, loaded in detector.py alongside sanitization-detection. Classifies each regex hit in context (a $ figure near "trial balance" is not a hit; one near "contract value" is) and drafts a generalization suggestion.

3

Data model

Migration adds COMMERCIAL_TERM to masking_dictionary.entity_type, and creates the new flagged_items table (run_id, flag_type, chunk_id, surface_text, suggested_action, status, reviewer_id, resolution, decided_at) — built once here, reused by every other flag-based gap below. reconciler.py routes COMMERCIAL_TERM hits to flagged_items instead of masking_dictionary.pending_approval.

4

Review UI + resolve path

New app/agents/sanitization/flags.py exposes flag_for_judgment.create/.resolve. ReviewDetailPage.jsx gets a new "Flagged for judgment" panel (keep / generalize / remove) next to the existing mask-candidate list.

5

Apply

On resolve="generalize", render.py substitutes the reviewer-provided generalized text at the recorded span — same span-replacement mechanism apply_masks already uses, just with free text instead of a dictionary token.

6

Regression

New fixture in scripts/regression_check.py: a planted dollar figure + a payment-term sentence, asserting both are detected and flaggable offline with zero Bedrock calls for the regex layer.

B · Infrastructure, Security & Credentials P2 (cheapest — can ship alongside P1)

1

Pattern library

New app/agents/sanitization/regex_patterns/infra_credential.py: IPv4/IPv6/CIDR patterns, internal-hostname shapes (*.corp.internal, *.local), and credential shapes (AWS-style keys, bearer tokens, connection strings, a generic high-entropy-string heuristic).

2

Wire into pre-pass

Runs inside ner_prepass.py as a third free, on-CPU pass alongside the existing regex/NER candidates — zero LLM cost, so this whole gap can ship independently of any Detector/skill change.

3

Data model + mandatory redaction

masking_dictionary.entity_type gains INFRA_IDENTIFIER (mask) and CREDENTIAL (written with mandatory_redaction=true directly — the exact field already enforced server-side for confirmed own-firm logo matches).

4

Orchestration enforcement

agent.py is extended so apply() ignores any reviewer attempt to exclude a CREDENTIAL entry — mirrors the existing mandatory_redaction override built for logo matches, applied to a new entity type rather than a new mechanism.

5

Image coverage

image_scan.py's existing per-image vision call gets a visible_credential_or_hostname boolean field — shared build work with Gap D below, sequence together.

6

Regression

Extend regression_check.py with a planted IP address, internal hostname, and fake AWS-style key in body text and inside one fixture image; assert mandatory redaction fires and cannot be unchecked via the review payload.

C · Data Samples in Screenshots, Datasets & Reports P1

1

Vision-call extension

image_scan.py: add contains_real_data_sample to the existing per-image structured call (same call, same cost) — prompt asks whether the image shows a dashboard/table/report with real operational or financial data, as opposed to a logo or generic illustration.

Sequencing & shared infrastructure

  • Build flagged_items once, in Gap A. Gaps C, E, F, and G all write to the same table — sequencing A first means every later gap is a skill/field addition against infrastructure that already exists, not a repeated schema change.
  • Sequence B, C, and D together. All three extend the same image_scan.py vision call with a new structured field — batching them into one prompt/schema change avoids three separate PRs touching the same file and the same per-image cost budget.
  • The governance gate (P3) depends on P1/P2. distribution_gate.evaluate has nothing meaningful to check until flagged_items exists and at least one gap is producing rows into it — it is deliberately the last piece built, consuming what the earlier gaps produce.
  • Every gap ships behind the existing regression suite. Each gap's fixture is added to scripts/regression_check.py before its corresponding code lands, the same offline-first discipline that caught real bugs (issues 16 and 17) before they reached a production run.
