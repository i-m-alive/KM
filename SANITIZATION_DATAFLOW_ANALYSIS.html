NAVIKNOW · INTERNAL ARCHITECTURE REVIEW

How the sanitization agent actually redacts a document

A traced walkthrough of the detect → review → apply → verify pipeline that removes client-identifying content from PPTX, DOCX, XLSX and PDF files — what each stage really does, where confidence numbers come from, and what would move accuracy the furthest.

Repo Naviknow Traced against commit 176bab9 Entry point app/agents/sanitization/agent.py Model read directly from source, not from prior docs
In short

It is not one AI agent deciding everything. It's a deterministic pipeline — extract, detect, mask, render, verify — where an LLM (Bedrock Claude) is called at exactly four bounded points: to classify candidate entities, to judge images, to summarize masked text, and to classify tags. Every mask is applied by plain code, never by the model. Every render is re-scanned by five independent, code-based verification checks before a run is allowed to be marked "complete." There is currently no measured precision/recall anywhere in the system — the 0.6 confidence gate is an acknowledged, untuned default — but the five-channel re-verification plus a 43-case regression suite is what actually stands in for accuracy today.

01 Dataflow

Two phases, one human gate in between

A document only ever moves through detect() and, after a reviewer approves the proposal (or the run is configured to auto-apply), apply(). Nothing is written to the actual file until a human — or an explicit no-review policy — has signed off on the entity list.

02 Detection signals

Four independent ways an entity gets flagged

No single detector is trusted alone. Regex and the dictionary sweep exist specifically because the LLM detector is not reliable enough to be the only signal — the dictionary's full-text sweep was added after a real run in which a weaker model proposed 3 entities against a prior run's 11, silently missing 6 already-approved client names.

Regex / pattern

deterministic

Emails, phone numbers, URLs, account/contract-ID shaped strings. Public domains (gmail.com etc.) excluded. Hit or no-hit — no confidence score, because none is needed.

ner_prepass.py

Presidio NER

deterministic, optional

PERSON / LOCATION / ORG entity spans, mapped onto the client-entity taxonomy. Degrades gracefully to regex + LLM only if Presidio isn't installed.

ner_prepass.py

Approved dictionary

deterministic, confidence 1.0

Exact/alias lookup plus an independent full-text sweep for every previously-approved entity — a deliberate safety net against the LLM under-proposing.

masking/dictionary.py

LLM Detector

Bedrock, self-reported confidence

A bounded tool-use loop that pages through document chunks via one in-process tool call and classifies new candidates against 6 entity types.

detector.py

Image detection is its own three-signal vote

Each image is judged by a vision model call, transcribed by OCR (run through the same deterministic detectors as body text), and hashed against a perceptual-hash table of previously-confirmed logos. A confident OCR or logo match overrides the vision model's own stated judgment and floors confidence at 0.95 — because the model's free-text description has repeatedly been observed disagreeing with its own structured answer. An own-firm logo/name match forces exclusion regardless of what the model claims.

03 Where the LLM actually gets called

Four calls, one client module, JSON-schema constrained every time

Tag classificationclassifier.classify()Masked summary/metadataTag(s) against controlled vocabulary

All four route through one module, llm/bedrock_client.py, against a configurable BEDROCK_MODEL_ID (Claude 3.5 Sonnet by default; production runs have also validated Haiku end-to-end at roughly $0.058 for a 57-image deck across both agents — deterministic guardrails are what make the cheaper model viable despite weaker structured-output reliability). The client has a specific repair path for a Haiku failure mode where the model echoes the JSON schema back as one object and appends the real answer as a second.

The model never masks anything itself. Masking, dictionary writes, and filing a document for review all live in plain agent code, never exposed to the model as a callable tool.

04 Masking mechanics

Redaction is code, not a model decision

Every detected span is resolved through one shared primitive (masking/spans.py) — longest-match-first, word-boundary matched, whitespace-tolerant across line-wrapped text — used identically by chunk-text masking, native-format rendering, and PPTX chart/SmartArt masking. This replaced three previously-independent implementations that only agreed by convention.

  • Run-boundary aware: a match spanning multiple text runs only clears the runs it touches, preserving formatting on everything around it — replacing an earlier approach that collapsed a whole match into a single run and broke styling.
  • PPTX-specific: shapes (including nested/grouped), tables, chart XML cache and its embedded worksheet, SmartArt diagram text, OLE-embedded documents (re-rendered recursively through the same per-format pipeline), speaker notes, and layout/master text.
  • XLSX-specific: text and image redaction happen in a single load-mutate-save pass, because openpyxl renumbers every image's internal name on save — doing it in two passes would silently break the second one.
  • PDF-specific: word-level matching (not substring/context-padding), so line-wrapped names and adjacent table-cell text don't produce false matches or misses.
  • Three replacement styles: token ([CLIENT_1]-style, traceable), black (solid block), remove — reviewer-selectable.
05 Verification

The system never trusts its own render

After rendering, the output file is re-extracted from scratch and checked across five independent channels — none of them assume the render step succeeded just because it didn't throw:

ChannelWhat it re-checksOn failure
TextAny masked surface string still present, word-boundary matchedblocking flag → run status completed_with_issues, never silently completed
ImagesFull re-scan of the rendered file's images
MetadatadocProps / PDF Info / XMP residue
CommentsLegacy + modern/threaded comments, tracked deletions
HyperlinksLink targets, not just display text

A run that fails re-verification gets one targeted repair pass (remediate.py) — re-scrub, re-redact exactly the flagged images, re-verify — and only then is allowed to flip to completed and auto-chain into the Tagging agent. There is one known asymmetry here worth flagging: remediation clears resolved flags retroactively; the normal apply() path does not appear to, so a run that later verifies clean through a second full pass can still show its original blocking flag in the record.

06 Accuracy — what's real and what's assumed

There is no measured precision or recall in this system today

A full search of the codebase turns up no F1, precision, recall, or accuracy figures computed against a labeled dataset. What exists instead:

NumberValueStatus
Sanitization confidence gate0.6unmeasured default
Tag confidence gate0.7unmeasured default
Logo phash — confident matchHamming ≤ 4engineering heuristic
Logo phash — needs human judgmentHamming 4–10engineering heuristic
Min OCR entity length4 charscollision-avoidance cutoff
Regression suite43 checkspassing, deterministic, no Bedrock calls

In plain terms: nobody has yet run this against a labeled corpus of "here are all the client names that should be caught" and measured what fraction it actually catches. The 0.6 threshold is explicitly documented as a guess that needs real reviewed-run data to tune. What substitutes for that today is structural, not statistical — the five-channel re-verification, the deterministic dictionary safety net, and the 43-case regression suite that plants known leaks (including deliberately adversarial ones like the word-boundary trap "RIA" inside "MATERIAL") and asserts they're caught pre-render and gone post-render.

That's a meaningfully different kind of guarantee than a precision/recall number: it tells you the pipeline catches every leak type it has been told to plant and never silently ships a residual on a rendered file, but it doesn't tell you the true miss rate on unseen documents — a novel client-name format or an image logo with no OCR text and no phash match in the reference table could still slip through undetected on the first occurrence.

If you want an actual accuracy number

You'd need three things this system doesn't have yet: a held-out set of real (or realistic synthetic) decks with every sensitive span hand-labeled, a scoring script that diffs the agent's proposed entity list against that ground truth, and enough reviewed production runs to see how often reviewers add entities the model missed versus remove ones it over-flagged — that reviewer-edit delta is actually already captured in apply() and is the cheapest source of real precision/recall data sitting unused today.

07 Known gaps

What's explicitly acknowledged in the code

  • open

    Excel threaded comments are not scanned or scrubbed — a deliberate, documented gap, not an oversight.

  • open

    Stale blocking flags from the detect phase can linger on a run that later verifies fully clean, reading as "still unsafe" to anyone scanning the flag list.

  • open

    Text-channel residuals can't be patched by remediation — text masking only happens during a full render from the original file, so a text-verification failure forces a complete re-run, not a targeted fix.

  • open

    Vision-model non-determinism: the same image can get a different judgment at detect time vs. verify time. Perceptual-hash dedup mitigates this but doesn't eliminate it.

  • resolved

    Chart / SmartArt / OLE text was a blind spot as of the optimization plan; the last commit closed it end-to-end (extraction, masking, and verification all cover it now).

  • resolved

    Run-boundary-aware masking replaced an earlier approach that collapsed matches into a single text run and visibly broke formatting.

08 Where to spend effort next

Optimization recommendations, roughly ordered by effort

Quick win

Turn on prompt caching for the detector

The Bedrock client already supports a cachePoint after the system prompt, but the detector's call site never passes cache_system_prompt=True. This is unused plumbing — flipping it on is close to free and should cut detector cost/latency on any multi-chunk document.

detector.py · bedrock_client.py
Quick win

Clear stale blocking flags after a clean remediation-free re-verify

remediate.py already has flag-clearing logic — the normal apply() path doesn't reuse it. Sharing that logic removes a real source of reviewer confusion (a flag list that reads "unsafe" on a file that's actually clean).

agent.py · remediate.py
Medium effort

Capture reviewer-edit deltas as a running accuracy signal

Every time a reviewer adds a missed entity or removes an over-flagged one in apply(), that's a labeled data point already sitting in the system. Logging it into a running precision/recall estimate turns the 0.6 threshold from a guess into something you can actually tune against real usage.

Medium effort

Close the Excel threaded-comments gap

Same relationship-graph technique already used for modern PowerPoint comments should transfer directly — it's a known, bounded gap rather than an open-ended one.

comment_scan.py · comment_scrub.py
Structural

Build a small labeled eval set

10–20 real or realistic decks with every client name, logo, and identifier hand-annotated, scored automatically against the detector's output. This is the only way to get an actual precision/recall number instead of a regression suite that only proves "known leak types are still caught" — it won't tell you about a leak shape nobody has thought to plant yet.

Structural

Index the logo reference table before it grows past low hundreds

Perceptual-hash matching is currently a full linear scan per image group. Fine at current scale; worth an LSH-style index before the reference table (which grows automatically on every approved redaction) becomes the bottleneck.

09 A note on the older design docs

sanitization_agent_design.html describes a different system than the one running today

Stale: the design doc describes a real MCP server subprocess exposing tools over JSON-RPC, and a third LLM sub-agent ("Reconciler") for alias resolution. Neither exists in current code — the detector's one tool is a plain in-process Python function, and dedupe/alias resolution is handled entirely in deterministic merge code with no LLM tie-breaker.

Also stale: XLSX is listed there as "deferred, designed separately." It's fully supported today, including sheet-name masking, cell values, and xlsx-specific comment/hyperlink/metadata handling.

Still accurate: the core principle that masking is code, never a model decision, and the entity-type taxonomy — both held up unchanged from design to current implementation.

PPTX_Sanitization_Optimization_Plan.md and SANITIZATION_AGENT_REPORT.html are the two documents that actually match current code — the optimization plan's entire P0/P1 list (charts, SmartArt, OLE, modern comments, run-boundary masking, unified span logic) is now shipped per the latest commit.
