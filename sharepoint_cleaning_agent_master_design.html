NaviKnow · Agent Platform A-03 Master Design v2 (consolidated)

SharePoint Cleanup Agent — hygiene for content NaviKnow doesn't own

The catalogue's third agent, and the first to reach outside NaviKnow's own storage into a live, shared, human-populated SharePoint tenant. It reads a file's own metadata before ever touching its bytes, funnels duplicate detection through cheap deterministic checks before any model call, gives a stale file a reversible archive landing instead of a binary keep-or-delete choice, and never deletes, merges, or touches a permission without an explicit, separately-accountable human approval. Every piece of that — extraction, chunking, dedup, archive, review — can be built and fully tested today, before any Microsoft Graph access exists, against a mocked Graph client and then a disposable sandbox tenant.

01

Where it sits — the first agent outside NaviKnow's own boundary

Sanitization (A-01) and Tagging (A-02) only ever touch documents already inside NaviKnow — uploaded to uploads/, rendered to outputs/. The Coordinator (A-04) only orchestrates those two. A-03 is the first agent that reaches into a live, shared, human-populated system it doesn't own: a tenant's SharePoint sites. That's a categorically different risk profile, and this design treats it that way throughout — slower to trust, harder to auto-apply, easier to reverse.

1
Sanitization (A-01) & Tagging (A-02) — built, operate entirely on documents already inside NaviKnow.
2
Coordinator (A-04) — built, minimal; chains A-01 → A-02 with one marker + one hook. No rule engine yet.
3
SharePoint Cleanup (A-03) — this document. Per the platform roadmap it is "blocked only on a Microsoft Graph app registration" and "should be built against a mocked graph.list_sites first" — i.e. design and build the whole pipeline now, wire in real Graph access later without changing the agent's logic.
4
Search (A-05) & Deck Drafting (A-06) — later, depend on sanitized/tagged volume, not on A-03.

Two jobs, kept strictly separate

Find hygiene problems in a connected SharePoint library — duplicates, stale content, empty folders, version sprawl, metadata gaps, oversharing — and, only under approval, fix the reversible ones.

It is not a sanitization tool. If a scan turns up a document that looks like it contains unmasked client-identifying content sitting somewhere it shouldn't, A-03 never redacts it — it flags the finding and hands the document to Sanitization (A-01) via the same auto_chain_to marker the Coordinator uses. One agent, one job, same discipline as A-01/A-02 never overlapping A-02's tag taxonomy or A-01's masking dictionary.

02

Scope & non-goals

"Cleaning agent" is a wide brief. This narrows it to content hygiene (ROT cleanup) and explicitly excludes adjacent problems that look similar but need different tooling, different owners, or don't exist yet elsewhere in the platform.

In scope

Content & library hygiene

Exact/near-duplicate files, stale/orphaned content, empty folders, excessive version history, missing or inconsistent metadata, broken/dead sharing links, and flagging (not fixing) oversharing and unsanitized content found in the wrong place.

Out of scope (v1)

Anything needing a different authority

Tenant-wide permissions administration, e-discovery/legal hold decisions, retention policy authoring, DLP rule authoring, site provisioning/migration, and permanently purging anything from a second-stage recycle bin. These stay with SharePoint/Purview admins and IT — A-03 only ever reads that state to decide whether it's allowed to act.

  • One connected site/drive per scan run. No tenant-wide crawl in v1 — every scan is scoped to an explicitly connected, governance-approved site.
  • Files, not lists/pages. v1 targets document libraries (drives/driveItems). SharePoint lists, pages, and Teams-wiki content are out of scope until there's a concrete need.
  • Never the source of truth for "is this safe to delete." Retention labels, legal hold, and sensitivity labels live in Purview/SharePoint; A-03 only ever queries them live and defers to them — it never overrides or caches a stale answer for a destructive decision.
03

Access model — how the agent reaches SharePoint at all

The background worker (backend/app/worker.py) has no interactive user sitting behind it — it's a headless polling loop. That rules out delegated (user-signed-in) Graph permissions entirely; A-03 must authenticate as an application, via the OAuth2 client-credentials flow against Microsoft Entra ID.

  • App registration. A dedicated Entra ID app registration (e.g. "NaviKnow SharePoint Cleanup"), owned by the tenant's IT/security team — this is the one hard external dependency the roadmap already calls out. NaviKnow cannot self-serve this; it needs a tenant admin to create the app and grant admin consent.
  • Client credentials. A client secret (simplest, fine for v1/dev) or an X.509 certificate (recommended for any production tenant — no secret to rotate/leak). Stored the same way AWS credentials already are in this codebase: environment variables loaded via python-dotenv, read by the standard MSAL credential flow, never checked into source or the masking dictionary.
  • Sites.Selected, not Sites.ReadWrite.All. The tenant-wide application permissions (Sites.Read.All / Sites.ReadWrite.All) would let the app see and edit every SharePoint site in the tenant the moment admin consent is granted — unacceptable blast radius for a background process. Sites.Selected instead grants nothing by default; access to each individual site is then granted separately via POST /sites/{site-id}/permissions, with an explicit read or write role. The app registration only ever sees the sites NaviKnow has explicitly connected — see §05.
  • MSAL for Python (msal) acquires and caches the app-only token; the Microsoft Graph SDK or plain requests calls the REST API. Neither exists in requirements.txt today — msal is the one new dependency this agent adds.

This is an IT dependency, not an engineering one

Nothing about A-03's design is blocked on writing code — the entire pipeline (extraction, detection, risk-tiering, review, apply, audit) can be built and exercised end-to-end against a mock. What's blocked is the tenant app registration + admin consent + per-site grants, which sit with the client's IT/security team. §25 lays out how to build fully before that dependency clears; §14 lays out how to prove it works before that, too.

05

Connecting a site — governed onboarding, not self-service

1
km_governance requests a connection from NaviKnow's admin UI, picking a site from a list fetched via the one-time Sites.Read.All call (or pasting a known site URL directly — no listing call needed).
2
Tenant IT grants the per-site scope — POST /sites/{id}/permissions with role read, using the app registration's own admin credentials (a step NaviKnow triggers via API but a human at the tenant ultimately owns, same as any other cross-org access grant).
3
A sharepoint_connections row is created (§23): status="active", permission_scope="read". Scans can now run in report-only mode.
4
Write elevation is a separate request. Only once a site's Tier-1 candidates have been reviewed for a while does km_governance request the write grant, upgrading the same connection row to permission_scope="read_write". Tier-2 (destructive) actions additionally require manage_eligibility_rules configuration for that site before they can even be proposed (§17).

Same shape as the masking dictionary and tag vocabulary

A connection starts narrow and grows only by explicit governance action, never by the agent inferring it needs more access. Nothing about this onboarding flow is agent logic — it's an admin/governance workflow the agent's scans simply become eligible to run under once it's done.

07

Risk tiers & the human-in-the-loop rule — the load-bearing guardrail

This is the one rule the whole design protects: whether a proposal requires human approval is decided by what the action is, never by how confident the model is in it. That's a deliberate departure from A-01/A-02, where review is confidence-gated — destructive actions on a tenant NaviKnow doesn't own don't get that discretion.

Tier 1 — reversible, low blast radius

May auto-apply if high-confidence

Empty-folder removal, version trimming (old versions only, current version untouched), metadata/naming standardization, broken-link reporting, and moving a stale file to archive with a courtesy notice first (§11). All fully reversible or non-destructive; SharePoint's own version history covers metadata edits. Follows Tagging's "conditional review" shape: auto-apply when unambiguous, pause for review otherwise.

Tier 2 — destructive

Always reviewed. No exceptions, no confidence threshold.

Delete, permanently remove, deduplicate/merge, overwrite/replace, moving an archived item on to deletion, and any permission change are Tier 2 by definition — hardcoded, not configurable per-agent-run. Every single Tier-2 candidate is filed as its own reviewable item; there is no "approve all 500 duplicates" bulk action. A reviewer sees each proposed deletion/merge individually before it can be applied.

  • Separation of duty, reused as-is. The review system already enforces that the identity that produced a run never approves it (backend/app/review/routes.py) — that guarantee carries over unchanged; A-03 adds nothing new here, it just relies on it more heavily.
  • Tier assignment is a protected, deterministic lookup (§15) — not something a prompt could talk the model out of, and not something a governance rule can downgrade (only which items are eligible to be proposed at all is configurable, via §17's eligibility rules — never whether a Tier-2 action needs review).
  • Confidence still matters within a tier — a low-confidence near-duplicate is simply a lower-priority Tier-2 item for the reviewer, never an auto-apply candidate regardless of how high confidence climbs.

Why this is stricter than A-01/A-02

Sanitization and Tagging operate on a document already safely inside NaviKnow; a mistake is recoverable from the original upload. A-03 acts on a live, shared tenant other people are using right now — the cost of an unreviewed bad delete or merge is borne by someone outside this system entirely. The design responds by removing discretion, not by trusting confidence scores harder.

08

Extracting metadata & content, by format

Two separate tracks, and every item gets the first one whether or not it gets the second. Track A — Graph metadata is universal: name, path, size, native hash, timestamps, owner, version count, sharing links, retention/sensitivity label. It costs one API call for the whole listing and needs no format-specific code at all. Track B — content extraction is selective: it downloads the file and parses its actual text, and only runs when a scanner needs to compare or read what's inside — near-duplicate scoring, metadata/naming suggestions, or the PII pre-pass that hands off to Sanitization.

Content extraction is a value-add, not a dependency

A format with no parser is never a hard failure — it just gets less analysis, the same way extract_chunks already raises UnsupportedDocumentError for Sanitization rather than crashing a run. Track A metadata alone is enough to detect staleness, empty folders, version bloat, and broken links; Track B only sharpens duplicate detection and metadata suggestions for the formats it covers.

09

Chunking strategy — the dedup funnel

Chunking here serves one purpose: deciding whether two files are "the same document" cheaply enough to run across an entire site, and only spending real compute — download, parse, model call — on the pairs that actually need it. Four tiers, each a filter over the survivors of the one before it.

A

Exact-hash match — free, from the listing itself

Graph's driveItem file facet already carries a content hash (quickXorHash or sha256Hash, depending on drive type) as part of the same delta listing used for everything else. Two items with an identical hash are byte-identical — no download, no chunking, no LLM call needed to know that. This is the entire Tier-1/Tier-2 "exact duplicate" detector.

B

Candidate pairing — cheap pre-filter before any download

Among non-identical-hash items, comparing every file to every other file is quadratic and pointless. Group by extension, then by size within a small tolerance (±5%) and modified-date proximity or shared folder — only pairs surviving this filter are ever considered "possible near-duplicates" worth the cost of Tier C.

C

Structural fingerprint — download once, compare cheaply

For surviving pairs, download and run the format-specific structural chunker (§08, Track B), concatenate the chunk text, and compute a fingerprint over shingles of it — MinHash or SimHash, hand-rolled in pure Python (no new dependency; Hamming/Jaccard distance is a few lines). Structure-preserving chunks matter here for a second reason beyond fingerprinting: when a pair is escalated to Tier D, the reviewer sees "slide 4" or "sheet 'FY24 Budget'", not an arbitrary character offset.

D

LLM judgment — the ambiguous middle band only

Fingerprint distance sorts pairs into three bands: clearly identical content (treat as Tier A), clearly unrelated (drop), and an ambiguous middle (different enough to not be a plain copy, similar enough to not obviously be coincidence). Only that middle band goes to the model, with the structural chunks as context, for a same-document-different-draft judgment, a confidence score, and a one-line reviewer summary.

v1 — ship this

SimHash/MinHash over structural chunks

Catches near-verbatim copies (renamed, re-saved, one slide added) — the overwhelming majority of real SharePoint duplication — with no new infrastructure and no per-comparison model call.

v2 — only if paraphrase-level dupes matter

Embeddings via pgvector

Catches substantially rewritten or translated duplicates that a shingle fingerprint misses. Add the pgvector extension to the existing Postgres instance rather than standing up a separate vector store — but only once fingerprinting alone shows a real gap; it's a heavier per-document cost for a case that's rarer in practice.

Chunks are a cache, not a record of truth

Extracted chunk text is derived data used to make a proposal, not the source of truth about the document — the file in SharePoint always is. Store chunk text with a short retention window (e.g. 30 days) rather than indefinitely; a completed or expired run doesn't need its extracted text kept around, only its hashes/fingerprints and the audit decision.

11

The archive tier — a soft landing for files nobody's touched in a while

Without this tier, a stale file only has two outcomes: leave it, or (Tier 2, reviewed) delete it. That's a wide gap — a file untouched for a year is rarely something anyone wants gone forever, but it's also not something that should keep cluttering an active library. The archive tier sits between the two: reversible, low-blast-radius, and — critically — it never quietly escalates itself into a deletion. Every path out of archive back toward deletion still passes through the same Tier-2 human review as everything else.

What "stale" means, precisely

  • Primary signal: lastModifiedDateTime. Always available from Graph, for every item, at zero extra cost — it rides along in the same delta listing as everything else (§08). A configurable per-site threshold (default 270 days) is the baseline staleness test, and every candidate this scanner produces has this signal.
  • Secondary signal, confirmed, not assumed: real last-accessed activity. "Not modified in a year" is not the same claim as "nobody has opened it" — a file can sit unedited while people still read it constantly. The plan for closing that gap is below.
  • Orphaned ownership. If the item's owner (createdBy, or an explicit library "Owner" column) has left the organization per a directory lookup, route the notice to km_governance instead of a specific person, and treat it as a higher archive priority — nobody remains who can say "keep this."

The plan for last-accessed tracking

Modified-date alone answers "has anyone edited this?" — not "has anyone opened this?" Graph has a real, per-item answer to the second question; it's just a second, separate call, not part of the free delta listing, so the plan spends it only where it's actually needed.

1

Cheap pre-filter first — modified-date threshold, as today

The deterministic staleness scanner flags candidates purely by lastModifiedDateTime, exactly as above. This costs nothing extra and narrows a whole site down to the small set of items actually worth confirming.

2

Confirm, per candidate only, via Graph's item analytics

For each stale candidate (never the whole site), call GET /drives/{drive-id}/items/{item-id}/analytics/allTime — the itemAnalytics resource returns real view/edit action counts, and its itemActivityStats sibling returns a timestamped activity history (who touched it, and when, most recently). This is the actual "last visited" answer, not a proxy.

3

Reconcile — a recently-viewed file is pulled back out of the candidate set

If analytics shows real activity inside a shorter secondary window (default 90 days), the item is not stale regardless of its modified date, and drops out of the archive-pending candidate list entirely. If analytics agrees nothing has happened, confidence on the candidate goes up, not down.

4

Graceful fallback where analytics isn't available

App-only (client-credentials) access to itemAnalytics has historically had permission-scope nuances that vary by drive/tenant configuration — this needs to be validated for real during the sandbox phase (§14, Layer 1) before any threshold decision depends on it. Where it's unavailable or denied for a given drive, the candidate falls back to modified-date alone, exactly as before, with a lower-confidence flag recorded in its evidence — never hidden, never treated as equivalent to a confirmed signal.

Cached, not re-fetched every scan

Analytics calls are per-item and not part of the bulk delta listing, so they're the one place this scanner doesn't reuse the "free" listing data — the same discipline as chunking (§09): cheap filter first, expensive confirmation only for survivors. Results are cached in the metadata store with a refresh interval (default weekly) rather than re-queried on every scan of the same site.

Where archived content actually lives

Phase 1 — recommended default

An in-SharePoint "_Archive" library

Same site, same Sites.Selected write grant already required for cleanup, same mechanism as the existing Quarantine folder. Permissions, version history, and sharing links inside the item survive a graph.move_item untouched. Restore is one Graph call; nothing new to secure or audit.

Phase 2 — opt-in, only at real scale

Export to Azure Blob cool/archive tier

Materially cheaper per-GB once a site's cold-data volume is large enough for storage cost to matter — but it steps outside SharePoint's native permission model entirely, needs its own access broker and lifecycle policy, and turns a one-click restore into a second system to build and audit. Gate this behind a double-cold rule: only for items that have already sat idle inside the Phase 1 archive library for a long time, never straight from Active.

The notice, not a bulk sweep

Moving a file to archive is reversible and low blast radius, so it's Tier 1 by the same rule that governs version trimming or empty-folder removal — it may auto-apply. But "may auto-apply" isn't "silent": a plain-language notice (an LLM skill, §16) goes to the owner or km_governance with a grace period (default 30 days) before the move executes, and a reply or a click resets the stale clock and keeps the file active. This is a courtesy, not a review gate — the archive move itself doesn't wait on a human decision the way a delete does, but a human always gets a chance to say no first.

Archive registry — visibility and control inside NaviKnow

Every archived item already has a row in archive_records (§23) — original path, archived path, reason, grace period, restore state. That table is what makes a NaviKnow-side registry possible without any new data model: an Archive Registry admin page lists every archived item across every connected site, independent of navigating SharePoint's own _Archive library directly.

What the registry shows

Read-only browse, search, and filter

Original path, archived-at date, size/type, archive reason (stale / orphaned-owner), notice/grace status, and days remaining until delete-eligible — per site, per connection, sortable and filterable. Reuses the same view_all_runs_org_wide-style visibility already granted to km_governance (§18).

What an admin can do from it

Restore directly; request deletion — never bypass Tier 2

Restore is low-risk and reversible, so it can be actioned straight from the registry (a graph.move_item back to original_path, same as any restore). Requesting permanent deletion from the registry does not delete anything itself — it files a normal Tier-2 cleaning_candidate, which still requires a separate reviewer's approval and a live retention/hold recheck at apply time (§07/§13), exactly like any other delete. An admin browsing the registry gets a shortcut to propose deletion, never a shortcut to perform it.

No admin exception to separation of duty

If the admin who requests a deletion from the registry also happens to hold approve_cleanup_actions, they still cannot approve their own request — the existing submitter-cannot-approve-own-run rule (§07/§13) applies to registry-initiated deletions exactly as it applies to scan-discovered ones. The registry changes where a delete request originates, never who's allowed to approve it.

12

Process — detect → eligibility filter → propose → review → apply → verify

Four things happen in every run, in order: read the tenant's own metadata about a file before ever touching its bytes (§08), run cheap deterministic checks over that metadata, only download and parse content for the small subset of items where content actually decides the outcome (§09), and only call the model for the smaller subset still where judgment — not arithmetic — is what's missing. Cost and risk both fall out of that ordering, not out of a separate "budget" bolted on afterward.

1
Scan. Delta-query (/drives/{id}/root/delta) pulls changed items since the connection's last cursor — full crawl only on first connect. No LLM cost yet.
2
Detect candidates. Deterministic scanners (§06) run over the listing: hashing for duplicates, age/owner checks for staleness, recursive emptiness, version counts, link resolution.
3
eligibility.check (protected, deterministic). Every candidate is filtered against that site's eligibility rules (§17) — excluded paths, minimum age, excluded file types, retention/legal-hold status queried live. Ineligible candidates are dropped before a reviewer ever sees them.
4
LLM pass (targeted). Only for near-duplicate confidence scoring, naming/metadata suggestions, and human-readable proposal summaries — never for tier assignment or the eligibility gate.
5
Review. Tier-1 high-confidence auto-applies; everything else — all Tier 2, and any low-confidence Tier 1 — files individually into awaiting_review via review.create_task.
6
Apply (approved items only). A live re-check of retention/legal-hold immediately precedes any Tier-2 graph.delete_item/merge call — approval from minutes or hours ago is never trusted as still valid without this re-check (same "trust nothing but the freshest source" discipline as Sanitization's revalidation pass).
7
Verify & audit. Before/after snapshot recorded to cleaning_action_audit; run completes (or completed_with_issues if anything Graph-side didn't confirm as expected).
  • Metadata first, content only on demand. Microsoft Graph returns a file's hash, size, dates, owner, version count, and sharing state as part of the same /delta listing used to detect changes — none of that requires downloading the file. Content extraction (§08) only runs for the minority of items a deterministic check has already flagged as needing a closer look.
  • The model is the last, smallest step. Every table in this document distinguishes "deterministic" work (hashing, date arithmetic, folder traversal — code, not a prompt) from "LLM-assisted" work (judgment calls with no clean formula). The ratio matters: on a typical site scan, well under 10% of candidates ever reach the model.
13

Guardrails — the master list

Structural, not prompted — every rule below is enforced in agent code or infrastructure, never left to a model's discretion. Grouped by what each one actually protects against.

Access & authentication
  • Sites.Selected, never tenant-wide. Every site is an explicit, separately-granted scope; read and write are separate, sequential elevations.
  • Purge permission is never requested, in any phase. SharePoint's native two-stage recycle bin (~93 days total) is the deliberate structural safety net under every delete — an absence of capability, the same pattern as Tagging having no fs.read_document tool.
  • Credentials never touch the masking dictionary, source, or logs. Same discipline as the AWS/Bedrock credentials already in this codebase.
  • No Graph scope for changing sharing or permissions is ever requested, in any phase. Oversharing (anyone-links, broken inheritance, external sharing beyond policy) is flagged, never fixed by this agent (§04/§06) — a human corrects it directly in SharePoint.
  • Prove it in a sandbox first, never against a real tenant. Every scanner, tier, and review path is exercised against a mocked Graph client, then a disposable Microsoft 365 Developer Program tenant seeded with synthetic ROT fixtures — never real client content — before any real tenant credential is requested. Full walkthrough, including why a TEE doesn't substitute for this, is in §14.
Action & review
  • Tier is decided by action type, never by confidence. Delete, merge, and permission change are always Tier 2 — no exceptions, no bulk approval, one candidate per review item; a reviewer cannot approve "all duplicates" in one action without seeing each one.
  • Archive-to-delete is never automatic. The only path from Archived to Deleted still passes through an individually reviewed Tier 2 gate (§11) — archiving buys time, it never spends down to deletion by itself.
  • Mandatory dry-run for a newly write-enabled site. The first scans after a site is upgraded to read_write run with applies force-disabled regardless of approval, so a reviewer can see what the agent would have done before it can do anything.
  • Separation of duty, reused, not reinvented. The submitter of a run can never approve its own review items (existing review-layer rule, §07).
Data, retention & reversibility
  • Retention & legal hold are hard, live blocks. Re-verified live, immediately before every Tier-2 apply call — never cached, and the result overrides even an already-approved review decision.
  • Quarantine or archive before any delete. A destructive action always lands somewhere recoverable first — the site-local NaviKnow Cleanup Quarantine folder for duplicates, or the _Archive library for stale content across its full grace-and-archive lifecycle (§11), well before it ever becomes delete-eligible — a second, NaviKnow-controlled recovery window layered on top of SharePoint's own recycle bin.
  • Unsanitized content is handed off, never redacted here. A PII pre-pass hit chains to Sanitization (A-01) via the existing auto_chain_to marker.
  • Before/after snapshot on every write. cleaning_action_audit records the item's metadata immediately before and after any write, regardless of tier — a manual recovery path even after a quarantine/archive/recycle-bin window lapses.
  • Soft delete only — on both sides, never a hard delete. On SharePoint's side, graph.delete_item only ever lands an item in the native two-stage recycle bin; on NaviKnow's own side, cleaning_candidates, cleaning_action_audit, archive_records, and eligibility_rules rows are never removed with a SQL DELETE — a row's lifecycle ends at a status flag (e.g. superseded/revoked), not at deletion. Whatever happens to the file, the record that it happened always stays in the system.
Extraction, cost & rate limits
  • Content is downloaded only when a deterministic pre-filter already justifies it. Never a bulk crawl-and-parse of an entire library just to build a fingerprint index (§09).
  • The model sees only the ambiguous middle band. Clear matches and clear non-matches never reach an LLM call.
  • OCR is opt-in per site, never speculative. Only runs on images already paired with a real document by cheaper signals first.
  • Graph rate limits are honored, not raced. 429/Retry-After responses trigger exponential backoff; batch reads go through /$batch; large scans run in off-peak windows so a crawl never competes with people actively using the site.

Testing in a controlled environment — before real SharePoint access exists

Two different questions hide behind "test it safely." One is what must already be proven true before anyone even asks a tenant for a real credential — a checklist, not a sandbox. The other is what environment the agent actually runs against while proving it — a set of progressively more realistic, progressively more isolated environments, never production and never a real client's content until the last, still fully governed step.

A one-time validation gate, not something that re-runs on every scan

Two different rhythms get conflated under "testing," and they need to stay separate. Continuous regression testing — the pipeline's unit/integration suite running against MockGraphClient — runs on every commit, forever, the same as any other software test suite; that's ordinary engineering hygiene, not a special gate, and it never touches a real tenant. What this section is actually about is different: a one-time, formal validation pass through the full layered sandbox below, done exactly once — before the agent is ever pointed at a real production tenant for the first time — not repeated on every subsequent real scan afterward.

What runs forever vs. what runs exactly once

Forever, on every commit: the unit/integration suite against the mock (Layer 0 below) — no tenant involved, no sign-off required, ordinary CI.

Exactly once, before Phase 1 of the build plan (§25), with a named sign-off: the full Layer 0→3 walkthrough below, ending in a documented go/no-go decision — km_governance, plus the tenant's security/IT team if they require it — that the agent is safe to point at a real, connected site. Once that gate is passed, ordinary production scans don't repeat this process; they're the agent doing its job under the guardrails this gate already proved out.

The one-time gate's checklist — signed off once, before Phase 1

  • Full pipeline passes its own test suite against MockGraphClient. Every scanner, both risk tiers, the eligibility gate, and the review-queue branch exercised end-to-end with zero tenant dependency (§25, Phase 0).
  • Destructive Graph calls are structurally unreachable to the model — verified, not assumed. A test asserts graph.delete_item / graph.move_item / graph.trim_versions are never registered as callable tools, the same guarantee §15 relies on.
  • eligibility.check and the live retention/legal-hold recheck are unit-tested against mock "under hold" fixtures — including the case where a hold appears in the window between approval and apply, not only the case where it was already there at proposal time.
  • Separation of duty is covered by a test, not only documented. Submitter-cannot-approve-own-run is asserted, reusing the existing review-layer guarantee.
  • Rate-limit/backoff logic handles a mocked 429/Retry-After without the run failing or hammering the retry.
  • A real, code-level dry-run flag exists (applies force-disabled) — not a TODO, not a config value nobody has wired up yet.
  • Credential handling has been reviewed: secret/certificate loaded only from the environment, never logged, never written into audit_log, never present in a chunk cache or an LLM prompt.

Layered sandboxes — each layer buys more realism, at more blast radius

0

Mock Graph client — no tenant, no network, runs in CI

MockGraphClient returns canned sites/drives/items/hold-status from fixtures. Every code path is exercised on every commit at zero cost and zero risk — this is where regressions get caught before anything else runs at all.

1

Microsoft 365 Developer Program sandbox tenant — a real tenant that isn't anyone's

Microsoft's free, disposable developer-tenant program provisions a genuine Entra ID + SharePoint Online tenant for exactly this purpose, optionally pre-seeded with a sample-data "content pack" (demo sites, users, files). It behaves exactly like a production tenant to the Graph API — same auth flow, same throttling, same delta-query semantics — with no real person's document ever in it. This is where msal, the app-registration flow, and a real Sites.Selected grant get their first genuine exercise.

2

Synthetic ROT fixtures, seeded on purpose

A developer tenant's sample data is generic, not messy in the ways a real library is. A small seeding script — itself using the same Graph write calls the agent will use — uploads deliberately duplicated files, creates empty folders, pushes an item through enough versions to trigger bloat, and back-dates modification where the API allows it. The full detection catalogue (§06) gets exercised against realistic mess, not just hand-built JSON.

3

One isolated site, inside the real tenant, read-only first

Only after Layers 0–2 pass does this become Phase 1 of the build plan (§25): a single non-production site, Sites.Selected read-only, applies still force-disabled. Still fully governed by the onboarding flow in §05 — "it's just a test" never skips that.

Gate to Phase 2 (real read-write pilot): a full read-only scan on the sandbox tenant's synthetic ROT matches expectations before a single real site is ever touched

What a Trusted Execution Environment would — and wouldn't — buy here

A TEE (Intel SGX, AMD SEV, AWS Nitro Enclaves) protects secrets and data while a program runs from a compromised host or hypervisor reading its memory. That's real and useful — but it answers "where does the production client secret live so an operator with host access can't read it," not "does the dedup logic or the archive lifecycle behave correctly." An enclave runs the identical code against the identical fake or real data either way; it doesn't make bad logic good, and it catches nothing the mock/sandbox layers above wouldn't already catch.

If the tenant's security posture calls for one, put it around the production worker process holding the real Graph credential — keep functional testing entirely in Layers 0–3, which is a separate concern from where the credential is held at runtime.

Isolation guardrails for the test environment itself

  • A dedicated Entra ID app registration per environment. The sandbox tenant's app registration and credential are never the same ones used against a real client tenant, and never reused across the two.
  • Test runs are tagged environment="sandbox" (or an equivalent connection namespace) so they're structurally impossible to confuse with a production run in the review queue, audit export, or cost dashboard.
  • Synthetic data only, always. Never copy a real client's documents into the developer tenant "to test with something realistic" — generate look-alike fixtures instead (Layer 2). The developer tenant is disposable and isn't a place to store real client content.
  • Sandbox credentials are time-boxed and rotated, same as any other non-production secret — a stale sandbox credential still working six months later is a bigger risk than the sandbox itself.
  • Automated test runs' network egress is scoped to the sandbox tenant's Graph endpoint only, so a config mistake can't silently point a test run at a real site.

Eligibility rules & governance

The RBAC matrix already reserves a manage_eligibility_rules capability for km_governance, unused until now — a strong signal this agent was anticipated. A-03 is what makes it real: a governed, per-site rule set that decides what's even eligible to be proposed, independent of and prior to the Tier 1/2 review gate.

  • Excluded paths. e.g. never touch /Legal or /Contracts regardless of what a scan finds there.
  • Minimum age thresholds. Per-site override of the default staleness/duplicate-eligible age (a brand-new site shouldn't have "duplicates" flagged from files uploaded an hour apart during initial migration).
  • Excluded file types / libraries. e.g. skip a library used as an active drop-zone even if its version counts look high.
  • Site-level write enablement. Whether Tier-1 auto-apply and Tier-2 proposals are even active for a site (independent of the read/write Graph grant in §04/§05) — a site can be read-connected and reported-on for a long time before cleanup actions are switched on.

Rules are a deterministic table, never an LLM judgment

Same reasoning as the Coordinator's deferred eligibility.check for contract restrictions — this is a rules table + deterministic check, not something the model decides at runtime. km_governance configures it; the agent only ever reads it.

Run lifecycle

Reuses the existing background-agent state machine unchanged — same worker, same review endpoints.

pending→ scanning→ awaiting_review→ applying→ completed / completed_with_issues
awaiting_review→ rejected · any state → failed
  • scanning — delta-query + deterministic scanners + eligibility filter + targeted LLM pass; heartbeats during long crawls so the stale-run reaper doesn't kill a legitimately slow tenant sync.
  • awaiting_review — every Tier-2 candidate and any low-confidence Tier-1 candidate parks here, each as its own reviewable item.
  • applying — live re-check of retention/hold immediately precedes each Tier-2 apply call; a blocking flag here (e.g. Graph reports the item now under hold) flips the run to completed_with_issues rather than silently skipping it.

End-to-end flow — a duplicate-cleanup walkthrough

1
km_governance submits POST /runs {agent_id:"sharepoint_cleaning", input:{connection_id}} → pending, returns immediately.
2
Worker picks it up → scanning. Delta-query lists changed items; Graph's own content hash finds two identical PPTX files in different folders — zero downloads yet.
3
eligibility.check confirms neither path is excluded and neither item is under retention/hold. Candidate proceeds; tier_of("duplicate") = 2.
4
review.create_task files the candidate individually → awaiting_review. A km_reviewer sees both file paths, dates, and the LLM's plain-language summary; approves keeping the newer copy.

6
Run completed. audit_log.write records the whole chain: found → eligible → reviewed by X → applied → quarantined at path, restorable on request.

Organize by entity — an opt-in foldering capability

Everything in §01–§25 is about ROT — content nobody wants. This is a different job: taking content people do want and putting it where it belongs — "there's a client, xyz — make a folder and put their files in it." It reuses this agent's connection, extraction, and review infrastructure, but it is opt-in, feature-flagged per site independent of cleanup, and off by default — moving active, currently-used content is a materially different risk than cleaning up already-identified garbage.

Two ways a plan gets created

Mode 1 — manual

An explicit rule, entered directly

An authorized user (create_organize_plan, §18) names an entity (e.g. "xyz"), a matching rule (e.g. "filename or path contains 'xyz'"), and a target folder path. The agent lists matching items via graph.list_drive_items and proposes moving each into the target — deterministic string matching, no LLM guessing involved.

Mode 2 — spreadsheet-driven

An uploaded Excel file with links + explicit destinations

The user uploads an .xlsx file where each row is a SharePoint link plus an explicit target-folder or entity-name column. The existing XLSX extractor (§08) reads the raw cell values; each link is resolved to a real driveItem via graph.resolve_share_link (§15); the plan is one proposed move per resolved row.

Feasibility of the spreadsheet-driven mode — an honest assessment

StepFeasibility
Reading the Excel file and pulling out raw link/URL cell valuesHigh — reuses the existing XLSX extractor unchanged; no new parsing capability needed.
Resolving a SharePoint link to a real driveItem via GraphMedium–high, conditional — Graph's shares API is a standard, documented capability, but it only resolves items on sites this app registration already has Sites.Selected access to (§05). A link into an unconnected site returns an access error, not a silent skip — it must be surfaced to the uploader as "can't reach this one," not swallowed.
Deciding which folder a file belongs in, from the spreadsheet aloneNot recommended without an explicit column — inferring the destination (e.g. guessing "xyz" from the file's content or name) is exactly the kind of judgment call this whole design keeps out of the model's hands for anything consequential. In a multi-client environment, a wrong guess isn't just clutter — it's potentially filing one client's content under another's folder. The spreadsheet must carry an explicit target-folder or entity-name column; the agent never infers one.
Moving many files across a live, actively-used library based on an uploaded fileHigh blast radius — Tier 2, always reviewed — unlike duplicate/stale cleanup, this acts on content people are actively using right now; a bad row in the spreadsheet moves something someone needed exactly where it was.

Review model — a reviewed plan, not itemized one-by-one

Every organize move is Tier 2 (§07) — never auto-applied — but reviewing it doesn't work like the accidental-duplicate queue, where each candidate is unrelated to the next. An organize plan is one intentional, human-directed batch: the reviewer sees the whole proposed mapping table (source → resolved item → target) in one screen, can edit or exclude individual rows, and approves the plan as a whole — while each resulting move is still logged and audited per item (§13), and still re-checked against eligibility and retention/hold live at apply time, exactly like everything else. Batch review is a concession to how the work is actually initiated, not an exception to individual accountability.

Guardrails specific to this feature

  • No LLM-guessed destinations, ever. The target folder or entity label is always an explicit input — a manual rule or a spreadsheet column — never inferred from file content or name.
  • Live re-resolution at apply time. A link resolved when the spreadsheet was uploaded is re-resolved immediately before the move executes — the target item may have moved, been deleted, or changed permissions since upload.
  • Eligibility rules still apply. Excluded paths, retention/legal-hold status (§17) gate organize moves exactly as they gate any other action — an item in /Legal doesn't become movable just because someone's spreadsheet says so.
  • Folder creation only under an existing write grant. graph.create_folder (§15) needs the same per-site write elevation as quarantine/archive — no new access is created for this feature.
  • Opt-in per site, independent of cleanup. A site can have duplicate/stale cleanup active without organize-by-entity being enabled, and vice versa — this is a separate switch in eligibility_rules (§17).
